# Модель данных Excel и Power Pivot

## Цели и требования

На занятиях 2.1 и 2.2 данные были собраны в чистые таблицы. Теперь их нужно организовать так, чтобы один набор фактов можно было группировать по разным признакам (точка, регион, категория, месяц) без дублирования описаний и без риска противоречий. Для этого в Excel используется модель данных.

После занятия нужно уметь:

- объяснять недостатки плоской таблицы и находить противоречивые описания;
- формулировать зерно таблицы фактов и отличать факт от измерения;
- добавлять таблицы в модель данных и создавать связи «один ко многим»;
- проверять ключи (уникальность, типы, полнота);
- настраивать порядок месяцев в сводной таблице;
- строить сводную таблицу из нескольких связанных таблиц и сверять результат.

> [!NOTE]
> Требуется Microsoft Excel 2021 или Microsoft 365 для Windows с доступной надстройкой Power Pivot. Если на ленте нет вкладки «Power Pivot», надстройка включается в «Файл» → «Параметры» → «Надстройки» → «Управление: надстройки COM» → «Перейти» → «Microsoft Power Pivot for Excel». Работа выполняется в файле `lesson-3.1.xlsx`; сохраненная модель понадобится на занятии 3.2.

## 1. Недостатки плоской таблицы

Лист «Плоская таблица» содержит 128 строк: продажи восьми точек по четырем категориям за четыре месяца (январь – апрель 2026). В каждой строке совмещены:

- сведения о продаже: дата, количество, выручка, прямые затраты;
- код, название, регион и формат торговой точки;
- код, название и группа категории.

Для сводной таблицы такая структура удобна: все поля уже в одной таблице. Но при сопровождении возникают три проблемы.

### Избыточность

Точка `TT03` продает четыре категории в течение четырех месяцев, поэтому ее название, регион и формат записаны 16 раз. На большем горизонте повторений станет больше. Повторяется не событие, а описание объекта.

### Аномалия обновления

Если у точки изменился регион, его придется исправить во всех строках точки. Пропущенная строка создаст у одного кода два региона, и никакая проверка формата это не обнаружит.

### Противоречие описаний

Учебная таблица содержит именно такую ошибку. Если отфильтровать `TT03`, в столбце «Регион» окажутся два значения: «Урал» (в 15 строках) и «Поволжье» (в одной). Это запись продажи за март в категории CAT4 на 414 500 руб.

> [!WARNING]
> Совпадение общей суммы не доказывает корректность разрезов. Суммарная выручка плоской таблицы равна 43 965 500 руб., как и должна. Но в сводной по регионам появляется четвертый регион «Поволжье» с этими 414 500 руб., а выручка Урала занижена на ту же сумму. Итог верен, разрез неверен.

### Решение

Описание объекта хранится один раз, а в строке продажи остается только код:

```excel
Плоская таблица:  продажа → код + название + регион + формат + суммы   (повторяется в каждой строке)
Модель данных:    факт → код + суммы
                  справочник → код + название + регион + формат         (один раз)
```

Разделение определяет, **где хранится смысл каждого поля**. Регион точки – свойство точки, а не продажи.

```quiz
question: Почему плоская таблица может дать верный общий итог выручки, но неверный отчет по регионам?
A: В плоской таблице нельзя использовать числовые поля в сводной
B: Один и тот же код точки может иметь противоречивые значения региона в разных строках
C: Power Pivot всегда изменяет исходную сумму выручки
D: Сводная по регионам автоматически удаляет повторяющиеся продажи
correct: B
explanation: Общий итог складывает те же строки. Группировка же использует регион каждой строки, и при противоречивых описаниях часть выручки уходит в неверную группу.
```

## 2. Таблица фактов, измерения, зерно и ключи

Листы «Факт_Продажи», «Спр_Точки», «Спр_Категории», «Спр_Календарь» содержат те же данные, разделенные на таблицы Excel с именами `FactSales`, `DimStore`, `DimCategory`, `DimDate`.

### Таблица факта

Таблица фактов содержит повторяющиеся наблюдения и числовые показатели, которые анализируются. В `FactSales`: ID записи, дата, код точки, код категории, количество, выручка, прямые затраты. Названий точек, регионов и категорий в ней нет. Числовые показатели (количество, выручка, затраты) называют **фактами**; коды и дата служат для связи с измерениями.

### Зерно

Зерно (*grain*) – точное определение того, что описывает одна строка факта. Для `FactSales`:

```excel
1 строка = 1 торговая точка × 1 категория × 1 месяц
```

В наборе 8 точек, 4 категории и 4 месяца, значит 128 строк. Зерно формулируется **до** построения связей. Если часть строк описывает отдельные продажи, а часть – месячные итоги, суммирование и средние становятся неоднозначными, а вычисления на занятии 3.2 дадут неверные результаты.

> [!NOTE]
> Перед загрузкой таблицы в модель смысл одной строки записывается одним предложением. Если для разных строк это предложение разное, таблицу нужно разделить.

### Измерения

Измерение – справочная таблица, описывающая объекты, по которым группируют и фильтруют факты. Одна строка измерения соответствует одному объекту.

| Таблица | Одна строка | Поля |
| --- | --- | --- |
| `DimStore` | одна торговая точка | код, наименование, регион, формат, дата открытия |
| `DimCategory` | одна категория | код, наименование, группа |
| `DimDate` | один месяц | дата начала месяца, № месяца, месяц, квартал, год |

### Ключи

В измерении код определяет ровно одну строку: `TT03` – одна точка. Это **ключ** измерения. В факте тот же код встречается многократно: это **внешний ключ**, ссылка на объект.

```excel
DimStore[Код точки]    TT03 → одна строка справочника
FactSales[Код точки]   TT03 → много строк продаж
```

Связывать следует по устойчивому идентификатору, а не по названию: название может измениться, содержать лишние пробелы или различаться по регистру (занятие 2.1).

### Отличие от слияния в Power Query

При слиянии (занятие 2.2) столбцы справочника физически копируются в каждую строку результата. В модели данных таблицы не объединяются: каждая хранит свои данные, а связь сообщает Excel, как сопоставлять строки при построении отчета. Поэтому справочник можно менять в одном месте.

```quiz
question: Где повтор кода TT03 является ожидаемым, а где дефектом?
A: Повтор запрещен и в FactSales, и в DimStore
B: Повтор допустим в DimStore, но запрещен в FactSales
C: Повтор допустим в FactSales; в DimStore код должен однозначно определять одну строку
D: Повторы допустимы везде, Excel выберет нужную строку сам
correct: C
explanation: Точка имеет много записей продаж, поэтому в факте ее код повторяется. В справочнике ключ обязан быть уникальным, иначе объект описывается несколькими строками.
```

## 3. Добавление таблиц в модель данных

### Что такое модель данных

Модель данных хранится внутри книги и обрабатывается компонентом, который сжимает данные по столбцам и держит их в памяти. Поэтому она работает быстрее обычных формул на больших таблицах и не ограничена размером листа (1 048 576 строк). Сводные таблицы могут использовать несколько таблиц модели одновременно.

### Добавление таблицы

1. Установить курсор внутри таблицы `FactSales` на листе «Факт_Продажи».
2. Вкладка «Power Pivot» → **«Добавить в модель данных»**.
3. Дождаться открытия окна Power Pivot.

То же выполняется для `DimStore`, `DimCategory` и `DimDate`. Таблицы «Плоская таблица» (`FlatSales`) и `DimStoreBad` в модель **не добавляются**: первая – учебный пример дефектов, вторая – учебный пример дубликата ключа.

Если данные приходят через Power Query, результат запроса можно загрузить в модель без листа: «Закрыть и загрузить в…» → «Только создать подключение» + флажок «Добавить эти данные в модель данных» (занятие 2.1).

### Два представления Power Pivot

- **Представление данных:** таблицы в виде вкладок, как листы. Удобно проверить состав и типы столбцов.
- **Представление диаграммы:** таблицы в виде блоков. Здесь создаются и проверяются связи.

> [!WARNING]
> Четыре таблицы в окне Power Pivot еще не образуют аналитическую модель. Пока связи не созданы, Excel не знает, как сопоставлять строки, и сводная будет показывать в каждой ячейке итог без разбивки.

### Практика

1. Добавить четыре таблицы в модель.
2. В представлении диаграммы убедиться, что их ровно четыре.

## 4. Связи, кардинальность и проверка ключей

### Один ко многим

Отношение между справочником и фактом имеет кардинальность «один ко многим»: одна строка справочника соответствует многим строкам факта. В модели три связи, и во всех сторона «многие» – `FactSales`:

| Измерение (сторона «один») | Факт (сторона «многие») |
| --- | --- |
| `DimStore[Код точки]` | `FactSales[Код точки]` |
| `DimCategory[Код категории]` | `FactSales[Код категории]` |
| `DimDate[Дата]` | `FactSales[Дата]` |

В представлении диаграммы связь создается перетаскиванием ключа измерения на соответствующее поле факта либо командой «Конструктор» → «Создать связь».

### Направление фильтра

Связь «один ко многим» передает фильтр в одну сторону: **из измерения в факт**. Выбор региона в сводной ограничивает строки факта, а не наоборот. Это поведение по умолчанию, и в учебной модели его менять не требуется.

### Уникальность ключа

Лист «Демо_дубликат» содержит справочник `DimStoreBad`, в котором код `TT08` встречается дважды («Точка №8 «Луговая»» и «Точка №8 «Луговая» (архив)»). Использовать такую таблицу как сторону «один» нельзя: Excel не может определить, к какой из двух строк относится продажа, и отказывается создавать связь.

Устранение: удалить архивную строку или привести справочник к единственной записи на объект. Проверка выполняется до создания связи (в Power Query: профиль столбца «различных» равно «уникальных», занятие 2.2).

### Типы и значения ключей

Поля связи должны иметь совместимые типы: код точки в факте и справочнике – текст; дата – дата. Различие в значениях (`TT03 ` с пробелом, `tt03`) нарушает сопоставление без ошибки. Аналогично, дата начала месяца и произвольная дата внутри месяца – разные значения.

### Полнота справочника

Если в факте встретится код, которого нет в измерении (новая точка), модель не сможет назначить ему регион. Такие строки попадают в сводной в группу «(пусто)». Это сигнал проверить полноту справочника, а не скрыть группу фильтром (занятие 2.2, антисоединение).

> [!WARNING]
> Модель не исправляет исходные данные. Если регион в `DimStore` указан неверно, модель согласованно отнесет все продажи точки к неверному региону. Ошибка станет не случайной, а систематической.

### Как работает фильтрация через связь

```excel
Выбран регион «Урал» в DimStore
          ↓
Отобраны коды точек этого региона
          ↓
Через связь отобраны строки FactSales с этими кодами
          ↓
Просуммирована выручка этих строк
```

Текст региона не копируется в факт: фильтр распространяется по ключам. Этот механизм определяет **контекст фильтра**, на котором основаны меры занятия 3.2.

```quiz
question: Что проверить в первую очередь, если связь «один ко многим» не создается?
A: Оформление заголовков сводной таблицы
B: Уникальность ключа на стороне «один» и совместимость типов полей
C: Сортировку таблицы фактов по выручке
D: Наличие столбца «Регион» внутри FactSales
correct: B
explanation: Сторона «один» должна однозначно определять объект, а значения ключей должны быть сопоставимы по типу и написанию.
```

### Практика

1. Создать три связи. Для каждой назвать таблицу стороны «один» и «многие».
2. Проверить уникальность ключей трех справочников.
3. Добавить `DimStoreBad` в копию модели, попытаться связать с фактом по коду точки и зафиксировать причину отказа. Удалить `DimStoreBad` из модели.

## 5. Календарь и порядок месяцев

В сводной таблице месяцы – текст («Январь», «Февраль»…). Текст сортируется по алфавиту: порядок будет «Апрель, Февраль, Январь». Чтобы месяцы шли хронологически, в Power Pivot задается сортировка по столбцу:

1. В окне Power Pivot открыть таблицу `DimDate` (представление данных).
2. Выделить столбец «Месяц».
3. «Главная» → «Сортировка по столбцу» → «№ месяца».

Сортировка сохраняется в модели и применяется ко всем сводным.

### Требования к календарю

В учебной модели факты помесячные, поэтому `DimDate` содержит четыре строки по числу месяцев. В моделях с датами по дням календарь строится иначе:

- одна строка на каждый день непрерывного диапазона (без пропусков);
- ключ – дата без времени;
- таблица помечается как таблица дат («Конструктор» → «Пометить как таблицу дат»);
- календарь содержит все нужные атрибуты (год, квартал, месяц, номер месяца, день недели).

Непрерывность нужна функциям сравнения периодов (например, «тот же период прошлого года»), которые рассматриваются в более сложных моделях.

## 6. Схема «звезда»

После создания связей `FactSales` располагается в центре диаграммы, `DimStore`, `DimCategory`, `DimDate` – вокруг:

```excel
                 DimStore
                    │
DimCategory ─── FactSales ─── DimDate
```

Такая организация называется **схемой «звезда»**: одна центральная таблица фактов и несколько измерений, связанных непосредственно с ней. В учебной модели:

- измерений три, связей три;
- сторона «один» – в измерении, сторона «многие» – в факте;
- прямых связей между измерениями нет.

Регион – характеристика точки, поэтому хранится в `DimStore`. Группа – характеристика категории, поэтому хранится в `DimCategory`. Чтобы сгруппировать продажи по региону и группе одновременно, отдельная связь «точка – категория» не нужна: оба признака доходят до факта своими связями.

Такую модель проще читать и сопровождать: новый атрибут точки добавляется в `DimStore` и сразу доступен для группировки.

> [!NOTE]
> Схема «звезда» не исправляет неверно выбранное зерно, дубликаты ключей и неверные атрибуты. Ее преимущество в ясности: для любого поля понятно, в какой таблице оно хранится.

### Порядок в списке полей

Ключи и технические поля факта (`Код точки`, `Код категории`, `Дата`, `ID`) в отчетах не нужны: группировать следует по полям измерений. Чтобы пользователь не выбрал не то поле, их скрывают («Скрыть из клиентских средств» в контекстном меню столбца в Power Pivot). Числовые столбцы (`Выручка`) остаются видимыми.

```quiz
question: Почему в схеме «звезда» не создают связей между измерениями (например, между DimStore и DimCategory)?
A: Excel не позволяет связывать две справочные таблицы
B: Измерения связаны через общий факт, а лишние связи создают неоднозначные пути фильтра
C: Связи между измерениями удаляют данные из факта
D: Связей между измерениями быть не может, так как в них нет ключей
correct: B
explanation: Измерения соотносятся друг с другом через факт: продажа указывает и точку, и категорию. Дополнительные связи создают несколько путей между таблицами, и результат фильтрации становится неоднозначным.
```

## 7. Сводная таблица из модели данных

Построение диаграммы – промежуточный результат. Главная проверка: корректно ли модель агрегирует.

### Сводная «Регион × Месяц»

1. «Power Pivot» → «Сводная таблица» (или «Вставка» → «Сводная таблица» → «Использовать модель данных этой книги»). В списке полей таблицы модели отображаются отдельными группами.
2. «Строки»: `DimStore[Регион]`.
3. «Столбцы»: `DimDate[Месяц]`.
4. «Значения»: `FactSales[Выручка]`, операция «Сумма».

Три поля взяты из трех разных таблиц и работают совместно благодаря связям.

### Сравнение с плоской таблицей

## 8. Проверка модели перед вычислениями

Прежде чем создавать меры, проверяется:

- зерно `FactSales`: точка × категория × месяц, 128 строк;
- в модели четыре рабочих таблицы;
- ключи справочников уникальны;
- три связи, прямых связей между измерениями нет;
- типы и значения ключей согласованы;
- сводная по регионам показывает три региона;
- общая выручка – 43 965 500.

> [!TIP]
> При неожиданном значении в сводной диагностика начинается с модели, а не с формулы: связи, ключи, зерно, уникальность. Исправление формулы без проверки модели ведет к правке не того места.

## 10. Итоги занятия

1. Модель данных состоит из связанных таблиц и не требует копирования описаний в каждую строку факта.
2. До построения связей определяется зерно: что означает одна строка факта.
3. Факт хранит наблюдения и внешние ключи; измерения – уникальные объекты и их признаки.
4. Все связи учебной модели – «один ко многим», сторона «один» в измерении.
5. Уникальность ключа, согласованность типов и полнота справочника проверяются до связывания: Power Pivot не исправляет плохие источники.
6. В схеме «звезда» измерения связаны только с фактом.
7. Совпадение общей суммы не доказывает правильность разрезов; регион берется из справочника, а не из строки факта.
8. Порядок месяцев в сводной задается сортировкой по столбцу.
